Явный SQL API · PostgreSQL 14–18 · Открытый исходный код

Один вызов. Два пути чтения.

Подходящее попадание возвращает сохранённую строку. Промах или обход кэша читает исходную таблицу. Ваши обычные запросы SELECT сохраняют существующий путь.

psql │ чтение по первичному ключу
-- Attach your table once.
SELECT local_cache.attach_table('public.items');

-- Read rows by primary key.
SELECT local_cache.mget(
  'public.items', ARRAY[42, 7]::bigint[]
);

Это ваш тип нагрузки?

Выбираете кэш? Сравните страницы PostgreSQL, строки, материализованные представления и Redis.

Стоит измерить

  • Повторяющиеся полные чтения по первичному ключу.
  • Небольшой горячий набор целых строк.
  • READ COMMITTED на одном доступном для записи основном сервере.
  • Приложение, способное вызывать явный SQL API.

Оставьте обычный SQL

  • Соединения, диапазоны, агрегаты или произвольные результаты запросов.
  • RLS, секционированные или унаследованные таблицы.
  • База данных, в которую нельзя установить нативное расширение.
  • Нагрузки без измеренной выгоды.

Перед началом

Заменяет ли это shared_buffers?

Нет. PostgreSQL кэширует страницы базы данных. Это расширение отдельно кэширует сериализованные целые строки по первичному ключу. См. сравнение путей чтения.

Кэширует ли оно обычные запросы SELECT?

Нет. Кэш SQL используют только явные вызовы local_cache.mget. Ваши существующие запросы сохраняют обычный путь выполнения PostgreSQL.

Заменяет ли это Redis?

Нет. Необязательная конечная точка RESP2 ограничена. Здесь нет универсального набора команд Redis, TTL, pub/sub или распределённой координации. Сравните пути cache-aside для PostgreSQL и Redis.

Как проверить обновления и откат?

В руководстве по инвалидации есть тест в двух сеансах. Выполняемый пример проверяет незакоммиченные записи, чтение собственных изменений, откат и зафиксированные обновления.
