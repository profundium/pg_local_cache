# Когда кэш строк PostgreSQL помогает {#when-a-postgresql-row-cache-helps}

База данных может отдавать каждую страницу из памяти и всё равно тратить время
на выполнение запросов, проверку видимости и построение результатов. Кэш строк
пытается убрать часть этой повторяющейся работы. Он также добавляет обработку
ключей, проверки кэша и затраты на сериализацию. Полезный вопрос — становится ли
полный запрос приложения дешевле для вашей нагрузки.

> **Примечание к выпуску от 04.10.2026:** SQL API `local_cache.mget(regclass, anyarray)` из 2.x удалён в 3.0.0; для чтения строк используйте RESP `MGET`.

`pg_local_cache` предоставляет явный RESP-эндпоинт `MGET` для чтения целых строк. Обычные запросы `SELECT` сохраняют штатный путь выполнения PostgreSQL. Поэтому прогретый кэш `shared_buffers` и прогретый кэш строк — разные условия эксперимента.

## Сначала зафиксируйте контракт результата {#result-contract}

Сравнивайте одни и те же ключи, столбцы и форму вывода. Если приложению нужны
только два столбца, сравнение этой SQL-проекции с сериализованными целыми
строками измеряет разную работу. Если вызывающие стороны ожидают дубликаты,
порядок входных данных и null для каждого отсутствующего ключа, включайте работу
по выравниванию в каждый клиент.

В сохранённом [исходном коде примера Node.js](https://github.com/profundium/pg_local_cache/blob/master/examples/node-postgres/queries.mjs)
есть подготовленный базовый запрос `ANY` и вспомогательная функция для
восстановления позиций входных данных. [Упорядоченный пример `WITH ORDINALITY`](ordered-batch-reads.md#explicit-positions)
показывает обработку позиций в SQL. Для обоих вариантов расширение не нужно.

## Меняйте за раз один параметр нагрузки {#workload-dimensions}

| Эксперимент | Что зафиксировать | Что он показывает |
|---|---|---|
| Повторные прогретые чтения | Ключи, форма результата, соединения | Повторное использование уже заполненных записей |
| Холодные или отсутствующие ключи | Распределение запросов и размер пакета | Затраты исходной таблицы и отрицательного результата |
| Большие пакеты | Общее число запрошенных ключей и форма полезной нагрузки | Выигрыш от сокращения обменов против работы по каждому ключу |
| Конкурентные записи | Соотношение чтений и записей и границы транзакций | Затраты на инвалидацию, повторное заполнение и видимость |
| Более широкие строки | Распределение ключей и размещение клиента | Сериализация, передача и обход из-за размера строки |

Недопустимое чтение вполне может использовать исходную таблицу. Изучайте
изменения счётчиков вокруг каждого эксперимента; низкая частота попаданий сама
по себе не указывает на сломанную установку. Держите счётчики SQL и RESP
отдельно. В [техническом справочнике](../docs/TECHNICAL.md#health-and-monitoring)
описаны `local_cache.stats()` и `local_cache.health()`.

## Используйте общий запускатель и изучайте свидетельства {#shared-runner}

После [quickstart](../docs/QUICKSTART.md) запустите сравнение из репозитория:

```bash
./examples/benchmark.sh all > comparison.json
python3 scripts/benchmark_report.py comparison.json
```

В [руководстве по бенчмаркам](../docs/BENCHMARKS.md) перечислены требования,
управление нагрузкой и метрики. Сохраняйте исходный JSON. Записывайте ревизии
расширения и стенда, версию PostgreSQL, машину, число соединений и размещение
клиента. Сравнивайте повторные запуски, распределения задержки и использование
ресурсов сервера вместе с пропускной способностью. Короткая проверка корректности
не является публикуемым результатом скорости.

## Принимайте решение на границе приложения {#application-boundary}

Подготовленный SQL и RESP `MGET` используют разные пути чтения и обработки результата. Выигрыш одного не доказывает выигрыш другого. Проверяйте каждый путь на реальном шаблоне запросов приложения: один результат не предсказывает производительность для всех нагрузок.

Оставляйте обычный SQL, если нужны соединения, проекции, блокировки, неподдерживаемые формы таблиц или если кэш не даёт измеримой пользы. Для повторного чтения целых строк по первичному ключу проверьте RESP `MGET` с той же клиентской работой, которую фактически выполняет приложение. Продолжите с [руководством по выбору кэширования](../docs/postgresql-caching.md) и [экспериментом с инвалидацией](../docs/cache-invalidation.md).
