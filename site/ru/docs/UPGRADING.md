# Обновление pg_local_cache с 2.x до 3.0.0 {#upgrade-pg_local_cache-from-2x-to-300}

В версии 3.0.0 удалена SQL-функция `local_cache.mget(regclass, anyarray)`.
Для чтения закэшированных целых строк используйте аутентифицированный RESP
`MGET`:

```text
MGET CRUD:app.public.items:{"id":42} CRUD:app.public.items:{"id":7}
```

Рабочие процессы RESP используют настроенную роль PostgreSQL. Они не
наследуют SQL-права, транзакцию или снимок приложения. Используйте SQL для
проекций, соединений, блокировок строк и чтений, которым нужна семантика
сеанса приложения. В [руководстве RESP](resp.md) описаны настройка клиента и
кодирование ключей.

## Порядок обновления {#upgrade-order}

1. Измените приложения так, чтобы они больше не вызывали SQL `mget`. Проверьте,
   что RESP `MGET` использует отдельную роль worker и соответствует нужной
   модели авторизации.
2. Установите пакет или библиотеку 3.0.0 для используемой основной версии
   PostgreSQL.
3. Если в 2.x `pg_local_cache.bind_address` указывал адрес вне loopback, до
   перезапуска привяжите listener к loopback и используйте локальный прокси или
   sidecar для удалённых клиентов либо явно задайте
   `pg_local_cache.allow_plaintext_network = on`, если в этой сети допустим
   незашифрованный трафик. Встроенный TLS появится в более позднем выпуске.
   Иначе RESP workers откажутся запускаться.
4. Перезапустите PostgreSQL, чтобы загрузить новую общую библиотеку.
5. Проверьте listener: `SELECT local_cache.health();` должен показывать
   `workers_running = workers_configured`. Отправьте RESP `PING` и ожидайте `PONG`.
6. Проверьте версию загруженной библиотеки:

   ```sql
   SELECT current_setting('pg_local_cache.binary_version');
   ```

   Результат должен быть `3.0.0`.
7. Подключитесь как суперпользователь базы данных в каждой базе с установленным
   расширением и выполните:

   ```sql
   ALTER EXTENSION pg_local_cache UPDATE;
   ```

Миграция удаляет и заново создаёт `local_cache.metrics()`, поскольку после
удаление счётчиков SQL API чтения изменило табличный тип результата. PostgreSQL
Пользовательские права на `local_cache.metrics()` сохраняются. PostgreSQL откажется удалять функцию, если от неё зависит пользовательский объект.
Миграция намеренно не использует `CASCADE`. Удалите или измените зависимые
представления и функции самостоятельно, затем повторите обновление.
Сохранённые C-функции заменяются на месте, поэтому их OID, права и триггеры
подключённых таблиц сохраняются.

## Откат на 2.0.4 {#rollback-to-204}

Скрипта понижения версии нет. Чтобы вернуться на 2.0.4, переустановите его
пакет, перезапустите PostgreSQL для загрузки старой библиотеки, отсоедините
все сопоставленные таблицы, затем заново создайте расширение в каждой базе и
подключите таблицы снова:

```sql
SELECT local_cache.detach_table('public.items'::regclass);
DROP EXTENSION pg_local_cache;
CREATE EXTENSION pg_local_cache VERSION '2.0.4';
SELECT local_cache.attach_table('public.items'::regclass);
```

Повторите `detach_table` и `attach_table` для каждой сопоставленной
таблицы. Перед откатом сохраните список подключённых таблиц и особые права,
выданные на расширение, чтобы восстановить их. Пользовательские объекты,
зависящие от функций расширения, могут помешать удалению с обычной ошибкой
зависимостей PostgreSQL; разберите такие зависимости явно.

## Путь поиска библиотек {#library-lookup-path}

В control-файле в `module_pathname` указано короткое имя библиотеки
`pg_local_cache`. PostgreSQL ищет её с помощью `dynamic_library_path`
(по умолчанию он включает `$libdir`). Если сервер переопределяет этот
параметр, до перезапуска добавьте каталог, куда пакет установил
`pg_local_cache`.
