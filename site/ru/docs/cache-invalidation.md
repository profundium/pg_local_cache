# Инвалидация кэша PostgreSQL с учётом транзакций {#transaction-aware-cache-invalidation-in-postgresql}

Одного удаления записи кэша недостаточно, если более раннее чтение может
заполнить её после удаления. Представьте: читатель начинает загружать старую
строку, записывающий сеанс фиксирует новое значение и инвалидирует ключ, а затем
тот ранний загрузчик публикует свой результат. Кэш должен отклонить и такую
позднюю публикацию.

implementation ограждает затронутые ключи или отношения на пути записи в базу
данных. Заполнение несёт сведения о поколении, поэтому после инвалидации его
можно отклонить. Положительные записи кэша также содержат сведения о видимости
кортежа. Недопустимая запись использует чтение исходной таблицы. См. [технический справочник](TECHNICAL.md#transaction-consistency) с описанием контракта.

## Проверка инвалидации между SQL и RESP {#test-with-two-sessions}

Запустите [локальную демонстрацию](QUICKSTART.md). Прочитайте строку 42 через RESP и запишите её revision. Затем обновите строку в PostgreSQL и зафиксируйте транзакцию:

```sql
BEGIN;
UPDATE public.items SET revision = revision + 1 WHERE id = 42;
COMMIT;
```

Триггер подключённой таблицы инвалидирует затронутую строку кэша при commit. Следующее чтение через RESP возвращает зафиксированную revision. Для проверки rollback начните ещё одно обновление и откатите его; RESP продолжит возвращать последнюю зафиксированную revision.

RESP-воркеры используют настроенную роль PostgreSQL и не разделяют SQL-транзакцию или снимок приложения. Проверка чтения собственных изменений должна выполняться через SQL в той же транзакции приложения и пойдёт обычным путём чтения исходной таблицы. RESP предназначен для отдельных чтений с ролью воркера.

Исполняемый [тест Node.js](https://github.com/profundium/pg_local_cache/blob/master/examples/node-postgres/demo.mjs) проверяет RESP-чтения вокруг записей PostgreSQL.

## Случаи, намеренно обходящие кэш {#cases-that-deliberately-bypass-the-cache}

`REPEATABLE READ`, `SERIALIZABLE`, восстановление, параллельное выполнение и
транзакции, записавшие сопоставленные данные, используют путь исходной таблицы.
Слишком большая строка может быть успешно возвращена без кэширования. Частота
попаданий около нуля не обязательно означает неудачную установку: проверьте
нагрузку и счётчики обходов.

Если приложению нужен `SELECT ... FOR UPDATE`, используйте обычную операцию PostgreSQL. RESP `MGET` не предоставляет блокировки строк и семантику SQL-сессии.

## Изучите причину промаха {#inspect-the-cause-of-a-miss}

От имени администратора используйте `local_cache.stats()` и `local_cache.health()`. Сравнивайте счётчики до и после контролируемого теста. Счётчики кэша описывают путь чтения RESP. После намеренных изменений DDL выполните документированную процедуру `reconcile_table` или `reconcile_all`, не предполагая, что старое сопоставление всё ещё описывает изменённую таблицу.
