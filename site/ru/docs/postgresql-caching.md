# Руководство по выбору кэширования PostgreSQL {#postgresql-caching-decision-guide}

«Добавьте кэш» может означать несколько разных изменений. Кэширование страниц
PostgreSQL, подготовленный SQL, кэш целых строк, материализованное представление
и Redis исключают разные части чтения. Отталкивайтесь от повторяющейся работы в
запросе, затем измерьте полный путь по [руководству по бенчмаркам](BENCHMARKS.md).

## Начните с повторяющейся работы {#start-with-the-work-you-repeat}

| Потребность | Первый вариант | Что меняется |
|---|---|---|
| Сохранять страницы таблиц и индексов горячими | PostgreSQL `shared_buffers` и кэш ОС | Меньше чтений хранилища; SQL всё равно выполняется |
| Многократно отправлять один оператор | Подготовленный оператор | Меньше повторного разбора и планирования; выполнение продолжается |
| Возвращать целые строки по первичному ключу | RESP MGET pg_local_cache | Повторно использует подходящие целые строки через аутентифицированный endpoint |
| Предварительно вычислять соединение или агрегат | Материализованное представление | Читает сохранённые результаты; обновление определяет свежесть |
| Разделять объекты приложения между сервисами | Внешний кэш, например Redis | Ключи, TTL и инвалидация управляются приложением |

### Страницы и подготовленный SQL {#pages-and-prepared-sql}

[`shared_buffers`](https://www.postgresql.org/docs/18/runtime-config-resource.html#GUC-SHARED-BUFFERS)
хранит страницы базы данных, а не окончательные результаты `SELECT`. Горячая
страница может убрать ввод-вывод хранилища, но PostgreSQL всё ещё планирует или
выполняет запрос, проверяет видимость и строит результат. [Подготовленный оператор](https://www.postgresql.org/docs/18/sql-prepare.html) может убрать
повторный разбор и анализ в одном сеансе. Он всё равно выполняется над текущим
состоянием базы данных, а его план может быть общим или пользовательским.

В [сравнении кэша строк](row-cache-vs-shared-buffers.md) показана работа,
остающаяся на каждом пути.

### Целые строки по первичному ключу {#whole-rows-by-primary-key}

pg_local_cache хранит сериализованные целые строки по полным первичным ключам в ограниченной общей памяти PostgreSQL. Доступ выполняется через аутентифицированный RESP MGET; обычный SELECT никогда не обращается к кэшу. Подходящие чистые чтения READ COMMITTED могут получить попадание, а при более строгой изоляции, записи в транзакции, восстановлении, параллельном выполнении или слишком больших строках используется PostgreSQL. RESP-воркеры используют настроенную роль БД и не разделяют SQL-транзакцию или снимок вызывающей стороны. Неподдерживаемые сопоставления таблиц отклоняются при подключении. Это конкретный путь чтения, а не кэш результатов произвольных запросов. См. [руководство по пакетным чтениям](batch-primary-key-lookups.md), [технический контракт](TECHNICAL.md) и [проверки транзакций](cache-invalidation.md).

### Представления и внешние кэши {#views-and-external-caches}

PostgreSQL [материализованные представления](https://www.postgresql.org/docs/18/rules-materializedviews.html)
сохраняют результат запроса в отношении и обновляют его по требованию. Они
подходят для повторяемых отчётов, агрегатов и соединений, когда расписание
обновления задаёт допустимую границу свежести. Они не заменяют кэш строк по
ключу.

Внешний кэш, например Redis, подходит для объектов приложения, общих для
нескольких процессов или сервисов. Приложение владеет ключами, сериализацией,
TTL и инвалидацией. См. [руководство по Redis cache-aside](postgresql-redis-cache.md).
[Quickstart](QUICKSTART.md) запускает `pg_local_cache` на `public.items`.
