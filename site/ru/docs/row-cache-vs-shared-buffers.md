# Кэш строк PostgreSQL в сравнении с shared_buffers {#postgresql-row-cache-vs-shared_buffers}

[`shared_buffers`](https://www.postgresql.org/docs/16/runtime-config-resource.html#GUC-SHARED-BUFFERS)
PostgreSQL содержит страницы базы данных. pg_local_cache отдельно хранит
сериализованные полезные нагрузки целых строк под их полными первичными ключами.
Страница, уже находящаяся в памяти, может устранить чтение из хранилища, но
запрос всё ещё должен сформировать результат из кортежей базы данных. Попадание в
кэш строк может вернуть сохранённую полезную нагрузку после проверок допустимости
и снимка.

Операционная система также может кэшировать содержимое файлов. В качестве
базовой линии используйте прогретую базу данных.

## Кэширует ли PostgreSQL результаты SELECT? {#does-postgresql-cache-select-results}

`shared_buffers` кэширует страницы, используемые запросом, а не его итоговый набор результатов. Подготовленный оператор повторно использует работу разбора и может повторно использовать план, но PostgreSQL всё равно его выполняет. pg_local_cache кэширует целые строки через аутентифицированный RESP `MGET`; произвольные результаты SELECT не кэшируются, а существующие запросы не переписываются. В примере Node.js показаны отдельные пути RESP и SQL.

## Сравнивайте работу, а не только среду хранения {#compare-the-work-not-just-the-storage-medium}

| Чтение | Оставшаяся работа |
|---|---|
| Подготовленный SQL по первичному ключу через прогретые страницы | Обработка протокола, выполнение плана, проверки видимости строк и преобразование результата |
| Попадание в кэш RESP MGET | Обработка протокола, преобразование ключей, синхронизация кэша, проверки снимка и возврат сохранённой полезной нагрузки |
| Промах или обход RESP MGET | Проверки кэша плюс запрос к исходной таблице; успешное подходящее заполнение может записать данные в кэш |

Попадание в кэш строк устраняет повторное выполнение запроса к исходной таблице и сериализацию целой строки. Проверки кэша и синхронизация тоже потребляют CPU. Рабочий процесс RESP использует настроенную роль базы данных; RESP не разделяет SQL-транзакцию или снимок вызывающего клиента.

## Учтите затраты {#costs-to-include}

Кэшированная строка занимает дополнительную общую память, даже если её исходная
страница уже находится в памяти. Расширение также поддерживает состояние
сопоставления и инвалидации. Обновления подключённых таблиц выполняют триггеры
расширения. Когда рабочий набор превышает ёмкость, кажущаяся оптимизация чтения
может превратиться главным образом в накладные расходы на промахи и вытеснение.

Демонстрация по умолчанию намеренно сравнивает горячий набор из 128 строк с 1 024
слотами кэша, а затем первый проход по 4 096 строкам. В [руководстве по бенчмаркам](BENCHMARKS.md) объяснены оба случая, а записи подключённых таблиц
измеряются отдельно.

## Когда приложение лучше оставить как есть {#when-to-leave-the-application-alone}

Сохраняйте существующий запрос, если его сквозная задержка уже приемлема, если
приложению нужна лишь небольшая проекция большой строки или если доминируют
соединения, диапазоны и агрегация. Сначала сравните обычный пакетный запрос с
текущими вызовами по одному ключу в приложении. Выигрыш от пакетной обработки не
доказывает выигрыш от кэширования.

pg_local_cache 3.0 требует явных вызовов RESP `MGET`, установки расширения и preload при запуске. Оно отклоняет таблицы с RLS, секционированием и наследованием.

## Кэш строк или внешний кэш? {#row-cache-or-an-external-cache}

Для данных, авторитетным источником которых остаётся PostgreSQL, эта схема
оставляет инвалидацию на пути записи в базу и не требует поддерживать протокол
cache-aside в приложении. Она не предоставляет общую семантику Redis.
Конечная точка RESP2 имеет ограниченный набор команд и отдельную
модель безопасности.

Кэш строк PostgreSQL не заменяет состояние приложения с TTL, pub/sub или
распределённую координацию. См. [технический контракт](TECHNICAL.md) и
[примеры транзакций](cache-invalidation.md).
